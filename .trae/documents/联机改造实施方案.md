# 铁路环游 —— 联机改造实施方案

## Context（为什么做、要解决什么）

单机基础玩法已经完整并验证通过：开局人数选择、逐个选色、按红黄绿蓝紫重排行动顺序、开局选任务卡、抽牌/认领路线/抽任务卡三选一、单动作约束、双轨规则、终局触发、终局结算（任务卡 ±分、最长连续路径 +10、平局判定）与结算面板。

下一步做联机。当前代码有两处结构性障碍必须先处理：

1. **回合推进由表现层协程驱动** —— [GameSessionView.cs](file:///d:/My%20project/Ticket%20to%20Ride/20260925/Ticket-to-Ride/Assets/Scripts/Presentation/GameSessionView.cs#L244-L285) 的 `AdvanceTurnAfterDelay()` 自己 `WaitForSeconds(1f)` 后调 `TurnManager.EndTurn()`。联机时「什么时候换人」必须由权威端决定，客户端只能接收结果。
2. **视图直接读领域对象** —— `GameSessionView.RefreshPlayerInfo()` 用 `GameState.CurrentPlayer` 刷新手牌与任务卡视图。联机时每个客户端只能看到自己的机密信息。

已确定的技术决策（用户已选定）：

- **自研 `ITransport` + 命令/全量快照**，不使用 Netcode for GameObjects / Mirror。理由：游戏核心是一个 `GameState` 对象而非一堆 GameObject，用官方方案会被迫把状态改造成 NetworkBehaviour 体系、侵入现有 DDD 分层。回合制 + 状态量小，全量快照带宽完全可接受。
- **主机即服务器**（listen server）。
- **里程碑 1：本地回环**（同进程内跑主机+多客户端）验证架构；**里程碑 2：局域网直连**（IP + 端口）。

预期结果：领域层（`Assets/Scripts/Domain/`）**一行都不改**，联机能力以新的 Application 层组件 + 表现层读取面改造实现。

## 设计要点

### 1. 前置重构：把「推进回合」搬到 Application 层

Application 层不能用协程，用「每帧 Tick + 计时器」。

```csharp
// Assets/Scripts/Application/IGameController.cs
public interface IGameController
{
    IMatchView View { get; }              // 只读视图面（见 §4）
    event Action Changed;                 // 状态变化信号，供表现层刷新
    void Submit(GameCommand command);     // 本地=直接执行；联机=发给主机
    void Tick(float deltaTime);           // 推进 1 秒延迟、拉取网络消息
}
```

- `LocalHotseatController`：`Submit` 立即调 `TurnManager`；若结果 `TurnPhase == ActionCompleted` 则起 1 秒计时器，`Tick` 归零后调 `EndTurn()` 并发 `Changed`。
- 新增 `GameLoopDriver`（MonoBehaviour）在 `Update()` 里调 `_controller.Tick(Time.deltaTime)`。
- `GameSessionView` 删除 `AdvanceTurnAfterDelay()` / `_turnAdvancePending` / `_turnAdvancePending` 相关逻辑，改为 `_controller.Submit(new GameCommand { Kind = CommandKind.DrawTrainCard })`。

### 2. 传输抽象与协议

```csharp
// Assets/Scripts/Application/Net/ITransport.cs
public interface ITransport
{
    int LocalClientId { get; }
    bool IsHost { get; }
    event Action<int, byte[]> MessageReceived;   // fromClientId（-1 = 主机广播）
    void SendToHost(byte[] payload);
    void SendToPeer(int clientId, byte[] payload);
    void Tick();                                  // LocalTransport 也走队列，不禁用即时分发
    void Shutdown();
}
```

消息格式：`[1B 版本][1B 消息类型][payload]`。序列化用自写 **`BinaryWriter` 小端二进制**（无反射、IL2CPP 安全、比 JSON 省一半带宽），集中放在 `MessageCodec`。

### 3. 领域引用 → ID 的转换规则（关键）

| 领域对象 | 传输标识 | 说明 |
|---|---|---|
| `Route` | `RouteVisual.RouteId`（string） | 场景里的 100 条路线已用 `route_城市_城市[_2]` 命名，看起来唯一；实现时加一次启动断言查重 |
| `TrainCarCard` | 颜色（+ 市场槽位下标） | 该类型**没有 Id 也没有重写 `Equals`**，同色牌完全等价 |
| `DestinationTicket` | `Id`（`destination_1..30`） | 主机用 `Dictionary<string, DestinationTicket>` 反查 |
| `Player` | `Id`（`player_1..player_5`） | 快照用 Id 而非下标 |

**必须遵守的约束**：`PlayerHand.RemoveCard()` 与 `Player.CanClaimRoute()` 内部是**引用相等**（[PlayerHand.cs:66](file:///d:/My%20project/Ticket%20to%20Ride/20260925/Ticket-to-Ride/Assets/Scripts/Domain/Entity/PlayerHand.cs#L66)、[Player.cs:118](file:///d:/My%20project/Ticket%20to%20Ride/20260925/Ticket-to-Ride/Assets/Scripts/Domain/Entity/Player.cs#L118)）。所以主机收到「用红红蓝认领 route_X」后，**必须从该玩家的 `Hand` 里取回真实卡对象引用**，绝不能 `new TrainCarCard(...)`。

### 4. 每玩家快照过滤

- **公开段**（发给所有人）：Phase、TurnPhase、CurrentPlayerId、TurnOrderIds、Players、市场明牌、三种牌堆计数、全部路线归属。
- **私有段**（`My*`，只发本人）：自己的手牌颜色、自己的任务卡 Id、抽 3 选 1 的中间态。

构造：`SnapshotBuilder.Build(GameSession session, string viewerPlayerId)`，主机对每个客户端各调一次。仅在状态变化后广播，不每帧发。

表现层不重建领域对象（`Player.Score` / `TrainCarsRemaining` / 市场内容都没有公开 setter，硬做镜像必然失真）。改为让 `IMatchView` 暴露只读数据面，把现有 6 个视图的 `Refresh` 签名机械替换：

| 组件 | 现在 | 改为 |
|---|---|---|
| `PlayerHandView` | `Refresh(Player)` | `Refresh(IReadOnlyList<TrainCarCard>)` |
| `DestinationHandView` | `Refresh(Player)` | `Refresh(IReadOnlyList<DestinationTicket>)` |
| `PlayerStatusBar` | `Refresh(IReadOnlyList<Player>)` | `Refresh(IReadOnlyList<PublicPlayer>)` |
| `DeckCountView` | `Refresh(TrainCarDeck)` | `Refresh(int count)` |
| `TrainCardMarketView` | 读 `GameState.TrainCarMarket` | `Refresh(IReadOnlyList<TrainCarCard>)` |
| `RouteVisual` | `Claim(PlayerTrainColor)` | 不变，改由快照驱动调用 |

### 5. 权威端命令处理

```csharp
void ApplyCommand(int senderId, GameCommand command)
{
    var playerId = _senderToPlayer[senderId];                    // 身份以主机映射为准
    if (!IsAllowedNow(playerId, command.Kind)) { Reject(senderId); return; }

    switch (command.Kind)
    {
        case CommandKind.DrawTrainCard:
            _session.TurnManager.DrawTrainCard();
            break;

        case CommandKind.TakeMarketCard:                          // 只收槽位，绝不收颜色
            var card = _session.GameState.TrainCarMarket.VisibleCards[command.MarketSlot];
            _session.TurnManager.TakeOneMarketCard(card);
            break;

        case CommandKind.ClaimRoute:
            var route = _registry.Get(command.RouteId);
            var cards = ResolveCardsFromHand(playerId, command.CardColors);   // 取 Hand 内真实引用
            if (!_session.TurnManager.ClaimRoute(route, cards)) { Reject(senderId); return; }
            break;

        case CommandKind.DrawDestinationTickets:                  // 阶段 1：中间态留在主机
            _pendingTickets[playerId] = _session.GameState.DestinationTicketDeck.DrawMany(3);
            break;

        case CommandKind.ChooseDestinationTickets:                // 阶段 2：只收 kept 的 Id
            var drawn = _pendingTickets[playerId];
            var kept = drawn.Where(t => command.TicketIds.Contains(t.Id)).ToList();
            if (kept.Count < MinKeepNow()) { Reject(senderId); return; }
            _session.TurnManager.ChooseDestinationTickets(player, kept, drawn.Except(kept).ToList());
            _pendingTickets.Remove(playerId);
            break;
    }

    BroadcastSnapshots();
}
```

防作弊要点：客户端提交的 `TicketIds` 会被主机与「实际发给他的那 3 张」求交集，所以既无法保留没抽到的票，也无法多留。超时未选则由主机默认保留前 `minKeep` 张，避免卡死。开局选色同样由主机校验颜色未被占用。

## 风险与第一版简化

**高风险点**

1. `RouteVisual.routeId` 的 Inspector 默认值是 `"route"`；场景里已逐条命名，但必须在 Step 2 加启动查重断言。
2. 任何「客户端传卡牌实例」的写法都会静默失败 —— 必须坚持传颜色/槽位，由主机解析真实引用。
3. 表现层迁移只要漏改一处，客户端就会读到别人的手牌（安全漏洞而非普通 bug），Step 5 要逐个组件核对。
4. 开局流程（选人数 → 逐个选色 → 逐个选任务卡）目前是表现层递归驱动，联机时必须改为主机 `Phase + ActingPlayerId` 驱动。
5. `LocalTransport` 如果即时分发会掩盖时序 bug，所以接口保留 `Tick()` 且走队列。

**第一版先简化（明确不做）**

- 不做断线重连与重连接管（断开即冻结该玩家）。
- 不做客户端预测与延迟补偿（回合制 + 1 秒停顿足够掩盖 RTT）。
- 不做增量快照（全量 + `Version` 去重）。
- 不做主机迁移、不做观战。
- 协议只带 1 字节版本号，不兼容直接拒绝连接。
